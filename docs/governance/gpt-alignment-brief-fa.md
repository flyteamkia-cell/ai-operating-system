# اصلاحیه‌ی وضعیت — برای هم‌ترازسازی طراحی

این سند برای رفع چند سوءبرداشت است. طرح «Phase 1 Alignment Request» بر مبنای فرض‌هایی نوشته شده که با وضعیت واقعی دارایی‌های موجود نمی‌خواند. هدف رد کردن آن طرح نیست — بخش زیادی از آن درست است — هدف این است که دوباره‌سازی چیزی که همین حالا وجود دارد و کار می‌کند اتفاق نیفتد.

---

## ۱. دو دارایی مستقل داریم، نه یکی

تا امروز دو چیز جداگانه ساخته شده که هیچ‌کدام از دیگری خبر نداشته است:

**الف) ریپوی AIOS** — یک ریپوی کامل روی GitHub، در فاز معماری. شامل: قانون اساسی پروژه (۹ ماده)، ۶ عدد ADR، معماری سیستم، مدل داده، roadmap با معیارهای پذیرش، اسپک ۴ ایجنت، یک پرامپت نسخه‌بندی‌شده، یک اسکیل، دو ورک‌فلو، schema دیتابیس SQLite، و چند فایل TypeScript.

**ب) اسکیل `viral-content-lab`** — یک اسکیل **کامل و نصب‌شده و کارکننده** روی حساب Claude. این نکته‌ی اصلی این سند است.

---

## ۲. مهم‌ترین نکته: چیزی که طرح پیشنهاد داده بسازیم، از قبل ساخته شده

طرح، ساخت یک «Content Intelligence System» با این جریان را پیشنهاد داده:

```
Raw Data → Evidence → Analysis → Validated Insight → Knowledge
```

اسکیل `viral-content-lab` دقیقاً همین را، به‌صورت اجرایی، از قبل دارد:

```
جمع‌آوری → موتور A (Teardown) → patterns.md → موتور B (Generation) → محتوا
                    ↑                                                    │
                    └────────── فاز ۴: نتایج واقعی برمی‌گردند ←──────────┘
```

نگاشت یک‌به‌یک:

| در طرح پیشنهادی | معادل موجود |
|---|---|
| Evidence Layer | ورودی موتور A (سواپ فایل + ترانسکریپت) |
| Intelligence Layer | موتور A + روبریک `teardown-framework.md` |
| Validated Insight / Rules | فایل `patterns.md` |
| Execution Layer | موتور B با ساختار خروجی مشخص (هوک/ساختار/CTA/سیگنال/ریسک) |
| Learning from performance | فاز ۴ — بخش «تأییدشده روی حساب ما» در `patterns.md` |

محتویات واقعی اسکیل:
- `SKILL.md` — ارکستراسیون ۴ فازه با قواعد غیرقابل‌مذاکره
- `references/teardown-framework.md` — روبریک ۷ لایه + تاکسونومی مکانیزم‌ها
- `references/hook-library-fa.md` — الگوهای هوک فارسی دسته‌بندی‌شده بر اساس مکانیزم
- `references/tone-and-voice-fa.md` — رجیستر، ریتم، کالیبراسیون واژگان مالی
- `references/platform-playbooks.md` — مکانیک اینستاگرام/تلگرام/یوتیوب
- `references/financial-integrity.md` — خط قرمزهای محتوای مالی
- `references/telegram-capture.md` — پروتکل کامل جمع‌آوری تلگرامی
- `viral-content-lab: scripts/analyze_swipe_file.py` — نرمال‌سازی متریک و رتبه‌بندی (اجرایی)
- `viral-content-lab: scripts/parse_telegram_export.py` — تبدیل اکسپورت JSON تلگرام به CSV (اجرایی)
- `assets/swipe-file-template.csv` — قالب ستون‌ها

**نتیجه:** لایه‌های Evidence/Intelligence/Execution نباید از صفر طراحی شوند. کار باقی‌مانده «اتصال» است، نه «ساخت».

---

## ۳. تصحیح فرض‌های نادرست درباره‌ی ریپو

- **«Prompt Engineer Agent»** وجود ندارد. چهار ایجنت واقعی: Performance Analyst، Market Signal، Content Strategist، Brand Curator.
- **«Skill structure اولیه»** — اسکیل `content-brief` با پیش‌شرط‌ها، رویه‌ی گام‌به‌گام و شرایط رد صریح نوشته شده، نه صرفاً ساختار خالی.
- **«Workflow اجرایی ندارد»** — از نظر *کد* درست است، اما دو ورک‌فلو با تریگر، اعتبارسنجی، سیاست retry، مدیریت خطا، لاگ و مسیر بازیابی به‌صورت اسپک کامل نوشته شده‌اند.
- **«Knowledge Base واقعی ندارد»** — درست است. ساختار پوشه‌ها و قالب front-matter آماده است اما محتوای برند خالی است (`status: draft`). این یک شکاف واقعی است.

---

## ۴. تعارض نام‌گذاری فاز — باید حل شود

ریپو از قبل یک **«Phase 1 — Foundation»** دارد که چیز کاملاً متفاوتی است: ingest داده‌ی اینستاگرام از API، بدون هیچ AI، با ۴ معیار پذیرش مشخص.

طرح جدید هم اسمش را «Phase 1» گذاشته اما محتوایش متفاوت است. داشتن دو «فاز ۱» متفاوت در یک پروژه، سردرگمی تضمین‌شده است.

**پیشنهاد:** طرح جدید به‌عنوان یک مسیر موازی نام‌گذاری شود (مثلاً **Track B — Content Intelligence**) که به API وابسته نیست، در حالی که Track A (زیرساخت داده‌ی اینستاگرام) روی roadmap باقی می‌ماند. مزیت این کار: Track B به هیچ‌کدام از بلوکرهای API وابسته نیست و همین الان قابل شروع است.

---

## ۵. اصلاحیه روی بخش جمع‌آوری داده

ساختار پیشنهادی (۵ شیت + ۵ تاپیک تلگرام) منطقی است، اما **schema ستون‌ها نباید از نو اختراع شود.** قالب موجود که هر دو اسکریپت پایتون با آن کار می‌کنند:

```
post_id, account, account_followers, platform, format, post_url, post_date,
topic, views, likes, comments, shares_sends, saves, duration_sec,
avg_watch_sec, retention_pct, transcript_file, why_i_picked_it, notes
```

پروتکل تلگرام موجود (هشتگ `#سواپ` + قالب پیام ثابت) هم از قبل تعریف شده و پارسرش نوشته شده است.

**پیشنهاد:** ساختار چند-تاپیکی طرح جدید حفظ شود، اما تاپیک‌های «رقبا» و «محتوای ما» دقیقاً از همین schema استفاده کنند تا پارسر موجود بدون بازنویسی کار کند.

---

## ۶. محدودیتی که در هر طراحی باید لحاظ شود

اینستاگرام **سیو و سند (share) پست‌های دیگران را به هیچ‌کس نشان نمی‌دهد** — نه از طریق API، نه با اسکرپینگ. برای پیج‌های رقیب فقط ویو، لایک و کامنت عمومی در دسترس است.

پیامدها:
- داده‌ی پست‌های خودمان ذاتاً باارزش‌تر از داده‌ی رقباست، چون متریک کامل دارد.
- مقایسه‌ی عددی بین متریک‌های خودمان و رقبا **بی‌معناست** و نباید در هیچ گزارشی انجام شود.
- تحلیل رقبا باید ساختاری بماند (شکل هوک، معماری کپشن، فرمت، ریتم انتشار)، نه رتبه‌بندی عددی مقایسه‌ای با ما.

این محدودیت پلتفرم است، نه محدودیت سیستم، و با هیچ اتوماسیونی حل نمی‌شود.

---

## ۷. قیدهای ثابت پروژه که هر طراحی باید رعایت کند

از قانون اساسی ریپو (غیرقابل مذاکره):
1. AI تصمیم نهایی نمی‌گیرد؛ انسان تأیید می‌کند.
2. انتشار در MVP دستی است.
3. هیچ ماژولی مستقیم به یک ارائه‌دهنده‌ی AI وصل نمی‌شود.
4. مستندسازی قبل از کد.
5. هر کار قابل‌محاسبه با کد انجام می‌شود، نه با مدل.
6. ساده‌ترین معماری که مسئله‌ی *امروز* را حل کند؛ انتزاع فقط با دلیل واقعی.
7. نقش اول، ایجنت بعداً — یک مسئولیت تا زمانی که تکرارشونده و پیچیده نشده، ایجنت مستقل نمی‌شود.

---

## ۸. درخواست مشخص

با در نظر گرفتن موارد بالا، طرح قبلی بازنگری شود با این جهت‌گیری:

1. لایه‌های Evidence/Intelligence/Execution از نو طراحی نشوند — به `viral-content-lab` موجود متصل شوند.
2. مشخص شود چه چیزی واقعاً **کم** است (نه چه چیزی باید ساخته شود).
3. نام‌گذاری فاز تصحیح شود تا با roadmap موجود تداخل نکند.
4. schema جمع‌آوری با قالب موجود یکی شود.
5. خروجی به‌صورت فهرست تسک‌های کوچک و مستقل باشد که هرکدام مستقیماً ارزش تولید کنند.
